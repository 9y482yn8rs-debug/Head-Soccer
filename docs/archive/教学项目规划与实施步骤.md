# 大头足球：教学项目规划与实施步骤

> 本文记录教学规划。后续经教师授权，现已完成首个可玩教师版，启动方法见 README.md；学生任务版与试卷尚未开始。
> 依据：现有《Big_Head_Soccer_项目说明.md》及目录中的游戏效果示意图。
> 原说明末尾的“当前开发任务：仅执行阶段 1”是旧的执行入口；本次按教师最新要求，仅整理后续工作。

## 一、先明确项目的三个目标

1. **游戏能玩，代码能读懂。** 使用 Python + Pygame，做一个学生能顺着阅读、逐步修改的小项目。结构允许适度拆分，但具体语句保持直白。
2. **先做完整教师版，再制作学生任务版。** 我们先完成核心游戏并验证，再挑出简单、直观、有成就感的部分留白，配套说明、提示和验收方法。
3. **以后用题目检验理解。** 根据最终代码和实际课堂任务出卷，考查代码作用、执行过程、条件判断、参数影响、错误分析和等效写法。

**可读性与教学价值、画面吸引力、基础玩法质量共同作为首版要求。** 面向少儿，Q 版角色、好看的 UI 和及时的动作反馈是激发学习兴趣的重要组成部分，需要从起步阶段一起设计。扩展功能数量放在后面；每一部分都要能说明白、改得动、看得到效果。

当前暂按学生已接触变量、条件、循环和基础函数来规划；类可以作为教师先解释的少量新知识。学生实际基础、课时和是否学过类，留待下一步确认，不在本轮据此编写正式课程或试卷。

## 二、现有资料如何调整

目前目录中只有说明文档和示意图，没有需要重构的现有代码。因此这里讨论的是实现前的架构选择。

| 现有方向 | 建议 | 原因 |
|---|---|---|
| Python + Pygame、本地双人对战 | 保留 | 操作和结果直观，便于现场演示 |
| 先简单图形、后正式美术 | 调整为基础逻辑与首版美术同步推进 | 首个可展示版本就有可爱的角色、完整场景和动作反馈；简单图形仅用于内部碰撞调试 |
| 多层 entities/systems/ai/features 目录 | 第一轮改为少量同级文件 | 减少目录跳转和模块关系负担 |
| Game、Player、Ball 等对象 | 优先只保留 Player、Ball 两个简单类 | 两个球员复用一套行为；主循环用普通函数即可 |
| 完整比赛、AI、技能、道具、打包 | 分成“核心必做”和“以后选做” | 不把远期目标都塞进第一套教学材料 |
| 学生任务主要是技能扩展 | 补充移动、跳跃、胜负判断等基础任务 | 基础功能同样有明显效果，且更适合初学者 |
| 蓄力、冻结球等列为学生任务 | 保留，但上调难度 | 涉及跨帧状态、计时、释放或恢复，不能默认属于简单题 |

本规划中“美术从起步阶段落实”的要求取代原说明中的“先简单图形、后正式美术”安排。原说明保留作历史参考，后续执行时以本次更新后的规划为准。

## 三、第一套“完整教师版”的范围

这里的“完整”指一局比赛能够开始、进行、结束并重新开始，不指完成原规划里的所有扩展。

**核心必做：**

- 同一键盘双人操作：左右移动、跳跃、面向和踢球。
- 风格统一的卡通球场、两个球门、红蓝两名 Q 版大头角色和足球图片。
- 足球重力、落地反弹、边界、球员碰撞和踢球作用范围。
- 进球判定、比分、90 秒倒计时、进球后重置。
- 清楚美观的开始界面、比分与倒计时、比赛结束面板、胜负或平局、重新开始按钮。
- 基础动作和反馈：移动、跳跃、踢球姿态，足球旋转、命中反馈、进球庆祝和按钮反馈。
- 集中参数、必要注释、运行说明与常见问题。

**完成核心后再选：** 更多角色和球场、音效、力度条、蓄力射门、AI、技能、道具、角色选择、打包发布。

界面数量保持精简，但每个界面都要有完成度。美术素材由教师侧准备，显示和动效采用易读的普通函数、状态判断和计时实现，让学生在好看的游戏中学习简单代码。

### 首版视觉与动效方案

参考现有示意图的粗轮廓、大头小身体、圆润造型、明亮蓝绿场景与红蓝队伍配色。实际游戏采用 1280 × 720 横版画面，上方显示比分和时间，中部为比赛区，底部或开始面板提供操作说明；不把参考图外围的大段介绍文字搬进游戏。

| 内容 | 首版制作范围 | 关键要求 |
|---|---|---|
| 球场背景 | 一张明亮的卡通球场，包含天空、看台、草地 | 比赛区域留白充分，足球和角色容易辨认；背景不画固定球员、足球、比分 |
| 两名球员 | 红蓝各一名 Q 版角色，准备站立、跑动、跳跃、踢球姿态 | 透明背景；同一角色各帧造型、画布尺寸、脚底基准一致 |
| 球门与足球 | 独立球门和透明背景足球 | 球门画面与有效进球区域对齐；球与背景有足够对比 |
| 比赛 UI | 队伍头像、比分面板、中央计时、操作提示 | 数字与中文由程序绘制，避免把可变文字烘焙进图片 |
| 开始与结束 UI | 标题、开始按钮、结果面板、再来一局按钮 | 使用统一圆角、描边、色彩；按钮有悬停或按下反馈 |
| 基础动效 | 跑动切帧、跳跃姿态、短暂踢球姿态、足球旋转、命中闪光 | 用少量图片和简单时间变量实现，不引入复杂动画框架 |
| 得分反馈 | 短暂庆祝文字、比分强调、少量彩纸或星星 | 效果结束后正常恢复，不能挡住关键操作信息 |

首批素材同时确定命名、尺寸、透明边缘和绘制基准，并在实际游戏尺寸下检查。图片加载和缩放集中在启动阶段；碰撞范围与装饰性轮廓分开定义，并保留教师可开启的碰撞框显示。字体需要支持中文，并记录素材和字体的来源及使用许可。

美术验收看实际游戏截图与操作效果：角色是否可爱统一，透明边缘是否干净，动画是否抖动，UI 是否清楚，足球是否容易追踪。单张概念图好看不等于可直接投入游戏。

## 四、代码结构：少量文件，职责明确

建议核心完成时采用以下结构；开发初期只创建实际用到的文件。

```text
headSoccer/
├── main.py          # 启动、事件处理、主循环、游戏状态和调用顺序
├── settings.py      # 窗口、颜色、速度、重力、时长等参数
├── player.py        # Player：球员数据、移动、跳跃、踢球范围、绘制
├── ball.py          # Ball：足球数据、运动、地面反弹、绘制
├── collision.py     # 球与球员、场地边界的碰撞处理及踢球作用
├── match.py         # 进球判断、胜负判断、比分与时间相关规则
├── ui.py            # 比分面板、按钮、提示和开始/结束界面的普通函数
├── resources.py     # 集中加载图片、字体，准备尺寸；不建立资源管理框架
├── README.md        # 安装、运行、操作、阅读顺序
└── assets/          # 首版即使用：images/ 图片、fonts/ 字体
```

教学说明和任务资料在核心稳定后放入 `docs/`。AI、技能等功能确实开始实现时，再决定是否增加文件。不要先建空模块。

### 每一部分负责什么

| 部分 | 主要职责 | 不应混入的事情 |
|---|---|---|
| main.py | 建窗口、创建对象、收集按键、按顺序更新和绘制、控制比赛状态 | 复杂碰撞计算、每个角色的运动细节 |
| settings.py | 提供有名称、有单位的参数 | 会随比赛变化的比分或速度状态 |
| player.py | 保存位置、速度、朝向、落地状态；实现球员动作 | 修改比赛比分 |
| ball.py | 保存足球位置、速度、半径；更新运动 | 决定哪位玩家获胜 |
| collision.py | 判断接触、分离重叠、改变足球运动；处理踢球命中 | 显示菜单或倒计时 |
| match.py | 判断是否进球、谁获胜，提供比赛规则函数 | 读取键盘、移动角色 |
| ui.py | 绘制面板、按钮、文字和界面反馈 | 修改足球运动和比赛规则 |
| resources.py | 启动时加载、缩放图片与字体，供绘制使用 | 每帧重新读取文件或控制游戏流程 |

主循环保管当前比分、比赛状态和开始时间；`match.py` 的规则函数尽量通过参数接收数据、返回结果。避免两个文件各自保存一份比分。进球后的对象重置由主循环统一调用。

背景由主循环直接绘制，比分和界面集中在 `ui.py`，角色与足球各自负责图片绘制。动作切换先写在对应对象里，只需少量状态与计时；不另外建立动画系统。这样视觉内容从第一版进入项目，也不会把主循环挤满。

### 学生应该能追踪一帧发生了什么

```text
读取事件和按键
    ↓
根据当前比赛状态决定是否更新
    ↓
更新球员 → 更新足球 → 处理碰撞和踢球
    ↓
检查进球、更新比赛时间和状态
    ↓
绘制球场 → 角色和球 → 比分、时间和提示
    ↓
显示这一帧
```

进球检查与左右边界反弹必须配合：球门开口不能被普通墙壁先挡住。具体顺序由教师版统一验证，不作为初学者自由拼接的内容。

## 五、语法和实现的教学约定

### 推荐使用

- 普通变量、常量、`if / elif / else`、`for`、`while`、普通函数。
- 清晰的分步计算，必要时多写几行，不追求最短代码。
- 英文变量名配中文解释，例如 `velocity_y` 表示竖直速度。
- 少量简单类，只使用容易讲解的 `__init__`、属性和普通方法。
- 明确导入需要的名称，避免 `from ... import *`。
- 函数做一件明确的事情，参数和返回值容易说清。

### 第一轮主动避免

- 继承体系、抽象基类、装饰器、自定义事件总线、组件系统和通用技能框架。
- 把普通判断压缩成多层三元表达式、复杂推导式或 lambda。
- 为减少重复而写难读的动态属性操作和“万能函数”。
- 一开始就使用多线程、异步、数据库、复杂配置系统。
- 大量类型标注和高级类型表达式；只有确实帮助理解时才补充。
- 多个模块之间互相导入，或用很多全局变量共享状态。

**简单类不等于复杂面向对象。** 两名球员需要相同的数据和动作，使用一个 `Player` 类有实际价值。教学时先把它解释为“把一个球员的数据和动作放在一起”，不扩展讲设计模式。若学生完全未学过类，可以先让学生只修改普通规则函数和参数，再逐渐进入类的方法。

### 统一时间与坐标约定

- 屏幕向右为 x 正方向，向下为 y 正方向，所以跳跃初速度是负值。
- 统一使用秒作为时间单位，速度使用像素/秒；`dt` 表示上一帧经过的秒数。
- 将运动拆成易读语句，例如先计算位移，再更新位置；不要不同文件混用“每帧速度”和“每秒速度”。
- Pygame 返回毫秒的地方，在清楚的位置换算为秒，并写注释。
- 位置计算保存小数，绘制时再转换为合适坐标，避免低速运动因取整丢失。

使用 `dt` 会增加一个知识点，但能让整个项目时间计算一致。先用“速度 × 时间 = 位移”解释，再让学生使用现成变量；不把帧时间处理作为第一道留白题。

### 注释重点

解释“为什么”和“规则”，而不是给每一行重复翻译。例如：为什么落地后要把速度归零、为什么只能在地面跳、为什么一次进球需要暂停检测。碰撞算法中的数学细节可以集中说明，学生不需要第一轮完全掌握。

## 六、先完成，再提取学生任务

建议采用“教师完整版本 + 按课次制作的任务版本”，不要在完整代码里不断手动删改而丢失答案。

1. 先完成并试玩教师版本，保留对应版本或明确的备份。
2. 为选中的功能确定一个小而稳定的修改位置。
3. 从同一份教师版本生成该课任务副本，只清空指定部分。
4. 保留函数名、参数、调用位置和必要的安全默认值。
5. 附任务说明、提示、验收步骤；教师另存参考答案。
6. 检查任务版能启动，并检查填回答案后能恢复预期功能。

初期可手工准备少量副本，不必先开发自动挖空工具。每份任务标明对应教师版，避免代码修改后答案与任务不一致。每次只发当前课所需的任务版，避免学生面对很多缺口无从下手。

**留白不应造成与任务无关的启动错误。** 例如跳跃任务未完成时，角色仍然可以左右移动，只是不会跳；胜负判断任务先返回“待完成”，结束画面仍能显示。不要直接删掉被其他文件导入的函数。需要返回值的函数不能一律用 `pass` 占位。

### 学生任务候选表

| 任务 | 难度 | 学生完成部分 | 教师预先保留 | 验收效果 |
|---|---|---|---|---|
| 更换角色图片或调整大小 | 入门 | 修改素材选择或尺寸参数 | 图片加载、绘制与必要碰撞同步逻辑 | 角色外观明显变化 |
| 左右移动 | 基础 | 根据方向计算位移 | 按键读取、dt、边界处理 | 按键能改变角色位置 |
| 跳跃 | 基础 | 落地判断与向上初速度 | 重力、落地处理 | 地面可跳，空中不能无限跳 |
| 胜负和平局 | 基础 | 比较两个比分并返回结果 | 比赛结束与结果显示 | 三种比分关系都正确 |
| 射门强度参数 | 基础 | 调整或计算射门速度 | 命中范围、朝向与触发规则 | 球能明显踢远，左右方向正确 |
| 倒计时显示 | 基础到中等 | 剩余时间计算与不小于零处理 | 开始时间、文字绘制 | 时间递减，结束时显示零 |
| 进球庆祝文字 | 基础到中等 | 条件判断、文字或颜色选择 | 进球事件和显示时长 | 得分后出现对应提示 |
| 完整蓄力射门 | 中等 | 力量增长、上限、释放和重置 | 输入边沿、力度条、踢球接口 | 按住变强，松开射门且力量重置 |
| AI 行动规则 | 中等到进阶 | 根据球的位置选择动作 | 公共球员动作与反应间隔 | 电脑能追球，行为有可见变化 |
| 冻结球等限时技能 | 进阶 | 状态切换、持续时间和恢复 | 稳定的计时与技能接入位置 | 技能生效且按时恢复 |

第一批建议选择：参数调整 → 移动或跳跃 → 胜负判断 → 射门参数 → 庆祝反馈。教师可以根据课时只选其中三项。不建议把碰撞分离、球门边界、进球防重复和整套技能系统作为最早的留白任务。

角色尺寸任务必须预先确保绘制尺寸与碰撞尺寸有明确关系；不能让学生只改画面后出现看不见的碰撞墙。

### 每项任务都配一张说明卡

说明卡包含：任务目标、运行后的效果、修改文件和函数、已提供的输入、需要返回或修改的内容、涉及知识点、分级提示、验收方法、常见错误。

例如“胜负判断”任务：

- 输入：左侧和右侧的两个整数比分。
- 输出：左侧获胜、右侧获胜或平局的约定结果。
- 修改范围：一个普通函数，不改界面绘制。
- 提示顺序：先比较大小 → 再处理相等 → 检查每条分支都有返回值。
- 验收案例：3:1、1:3、2:2，分别得到正确结果。
- 理解追问：如果遗漏相等情况，调用者可能得到什么？

## 七、后续实施步骤与阶段交付

| 0. 明确首版设计 | 确定视觉布局、首批素材规格、基础玩法与文件职责；记录教学假设 | 一页首版设计说明、素材清单 | 美术和玩法范围具体，可据此制作 |
| 1. 制作美术与基础可玩版本 | 制作并接入 Q 版素材；实现移动、跳跃、踢球、基础碰撞、UI 外观与基本动作反馈 | 首批素材、可运行版本、实际游戏截图 | 画面有吸引力，双方可操作，球可被踢动，基础运动稳定 |
| 2. 完成一局比赛 | 接通计分和90秒计时、进球庆祝、重置、开始与结束界面及按钮 | 核心教师版 | 能完整玩一局，结果正确，可重新开始，视觉反馈完整 |
| 3. 教学可读性整理 | 检查命名、函数职责、语法难度、注释与阅读顺序 | 整理后的教师版、代码导读 | 能讲清每帧流程，简单功能修改范围小 |
| 4. 试做少量学生任务 | 先挑 3—5 个任务，制作安全留白与任务卡 | 任务版、教师答案、验收清单 | 未填写时能启动，填入答案后效果明确 |
| 5. 小范围试教 | 观察阅读、操作和排错过程，调整提示和任务粒度 | 修订版材料 | 学生能理解自己改了什么，而非只照抄 |
| 6. 制作考查材料 | 从已定稿代码提取题目，设置基础题与迁移题 | 学生卷、答案与评分依据 | 每题对应实际学过的知识，答案可核对 |
| 7. 按需要扩展 | 更多美术、音效、AI、蓄力或特殊技能，一次加入一项 | 可选拓展课 | 不破坏已有教学版本和任务接口 |

步骤 1 和步骤 2 可以分两次开发验收。每次先试玩确认，再推进；不要等所有扩展完成后才整理教学材料。现阶段不承诺具体课时，待学生基础和第一批任务确定后再估算。

步骤 1 中可以先展示一个实际素材搭配的静态场景确认风格，再接入运动与碰撞，但这些属于同一个首版工作阶段。尚未接通的比分与计时要注明为界面预览，不能当作已实现功能。学生基础与课时在制作任务版前确认，不妨碍先完成教师版的视觉与核心玩法。

### 核心教师版重点验收

- 两个玩家的移动、跳跃、朝向、踢球分别有效；现场检查常用组合键是否受键盘同时按键限制影响。
- 球落地不会持续陷入或异常抖动，角色不能无限空中跳跃。
- 球门有效高度、完全越线规则清楚；一次进球只计一次；左门失球记给右方，反之亦然。
- 球在门口可以得分，在有效球门区域外按场地规则反弹。
- 进球后位置、速度和踢球临时状态复位；重开后比分和时间全部复位。
- 时间结束后停止比赛更新；平局也有结果显示。
- 连续完成几局，并检查高速射门、球贴边、连续按踢球等情况。

倒计时在进球暂停时是否继续、到时与进球同一帧时谁先判定，要在步骤 2 开始前写成明确规则。建议第一版按比赛开始后的实际时间计时，进球短暂停顿也计入 90 秒；时间到达时先结束比赛，不再接受该帧新进球。规则可以调整，但代码、任务和答案必须一致。

## 八、以后如何从项目生成试卷

试卷应来自稳定的教师版和实际完成的课堂任务。现在只设计题型方向，不提前生成整套试卷，以免最终代码不同导致题目失效。

| 题型 | 考查内容 | 示例方向 |
|---|---|---|
| 解释代码 | 变量、条件和赋值的作用 | 为什么落地后把竖直速度设为 0？ |
| 跟踪执行 | 按顺序计算变量变化 | 给定初始位置、速度、dt，计算下一帧位置 |
| 等效改写 | 理解表达式和条件 | 对普通数值变量比较 `x += step` 与 `x = x + step` |
| 补全代码 | 完成一个局部功能 | 填写跳跃限制或胜负判断 |
| 找错改错 | 找出逻辑错误并解释现象 | 为何按住跳跃键会一直飞起来？ |
| 参数预测 | 联系代码与画面 | 重力增大、跳跃初速度不变，会有什么变化？ |
| 小型迁移 | 将已有逻辑用于新需求 | 给射门力度添加上限，或给提示添加条件 |

等效写法必须说明变量类型和使用前提，不笼统宣称两段代码在所有情况下都等价。运动计算题必须给出更新顺序、单位和初始值，避免存在多个合理答案。

每道题保存：来源功能或任务、知识点、难度、标准答案、可接受的其他写法、分步评分依据和常见误区。既考“写出了什么”，也考“为什么这样写、画面会怎样变化”。试卷长度和分值在课时、学情明确后决定。

## 九、建议下一次从哪里开始

**建议下一项工作是“首版视觉与基础玩法设计包”，确认后再执行。** 这项工作把后续制作所需的选择一次说明白，内容包括：

1. 以现有示意图为参考，确定红蓝两名 Q 版角色、卡通球场和 1280 × 720 比赛界面的布局。
2. 列出首批可用素材及规格：背景、两名角色的动作帧、球门、足球、头像与 UI 元素；区分图片素材和程序绘制内容。
3. 明确基础玩法：移动、跳跃、踢球、碰撞范围、球门位置；对应标出角色绘制基准，避免美术与碰撞错位。
4. 确定首批动效及简单实现方法，给出各文件职责和首版验收清单。

该设计包已在教师确认后完成，见同目录《首版视觉与基础玩法设计方案.md》，包含布局草图、素材规格、玩法与验收清单。下一项建议为首批真实素材与场景搭配预览，再据此开发基础可玩版本，不把一个只有占位方块的版本作为面向学生的首个展示成果。当前尚未生成素材或编写代码。

核心比赛完成、可读性整理和试玩通过后，再制作学生任务版。这样教师掌握完整答案，学生得到的每一个缺口也都有明确目的、可见效果和可核对的完成标准。
